# Decision: Ouro Feel, measuring how an app feels in real use

Status: proposed, 2026-11-04. The code lives in web, `ourostack/ouro-ui`, under `feel/`; this record is its design.

## Why

Ari, 2026-11-04: "being able to measure actual usage properly so that we could have gotten this right from the very start is something we should have cheap reusable fast deterministic tooling for, as part of ouro ui, yes?"

A chat app built on Ouro UI shipped a scroll regression that unit tests and headless browsers missed. Bisecting it taught two things. Single timing runs of the same build swung from 1.3 s to 26.6 s, so one run decides nothing. The signals that did catch it were deterministic: one frame of about 9 s, and the reader's message jumping 8.5k to 11k px when older history was put in above it. Ouro Feel makes those signals cheap to get for every Ouro component and every Ouro app.

## Decision

1. **The real engine decides.** A measure that gates a release comes from WKWebView on macOS or WebView2 on Windows, the engines Ouro apps ship in. Playwright's WebKit and Chromium on Linux are a fast first pass on pull requests; they catch most regressions and decide nothing about timing.
2. **One probe, any host.** The meter is one plain script, `ouro-feel-probe.js`, that a host injects before the page's own scripts: Ouro Feel's own minimal WKWebView host for components, Playwright for the Linux pass, and an app's own shipped web view (its probe service injects the same file) for app gates. It exposes `window.ouroFeel` and reports one JSON result per case through whatever channel the host has (`webkit.messageHandlers`, `chrome.webview.postMessage`, or a return value).
3. **Deterministic measures first.** Counts and pixels, which give the same answer on every run of the same build:
   - `forced-layouts`: layout reads (the properties and methods that make the engine lay out, such as `offsetHeight` and `getBoundingClientRect()`) made while a DOM write since the last frame is still pending. The probe sees a pending write with a document-wide `MutationObserver`'s synchronous `takeRecords()`, and clears it at each frame.
   - `layout-reads-per-frame`: the most layout reads in one frame.
   - `anchor-jump-px`: the most the reader's anchor (the message they are reading) moved on screen in any frame when they did not scroll. Safari has no Layout Instability API ([MDN's compatibility data](https://github.com/mdn/browser-compat-data/blob/main/api/LayoutShift.json) lists no Safari version), so the probe measures the anchor itself, in every engine alike.
   - `layout-shift-px` and `layout-jumps`: the same for every row in view, summed, and the count of frames where anything moved more than 1 px.
   - `blank-frames`: frames where the scroller's visible area holds no row.
   - `rows-mounted`: rows added to the page during the case.
   - `commits-per-input`: React commits per scripted input, from React's DevTools hook, which an injected script can install before React loads.
4. **Time measures are a median of at least 3 runs, with their spread.** Input to next paint, long tasks and launch time are reported as the median and the range of the runs, never one run. The longest frame is kept as a deterministic-enough guard: a frame over 1 s fails whatever the median says, because that is what the 9 s frame was.
5. **Seeded, made-up data.** Generators build heavy stores (long histories, many pictures and cards, live arrivals) from a seed, so every run gets the same data. Nothing comes from a real account; agents in the data have role names such as `inbox-agent`.
6. **Scripted human input from the host.** Trackpad scrolling with momentum, typing at 120 words a minute, conversation switches, cold and warm launch, a network drop and a wake. On macOS the host posts real events to its own window; the Linux pass uses Playwright's input.
7. **Cases keep the app's names.** The first app gate's cases are `launch-cold`, `switch`, `scroll` and `typing`, and Ouro Feel uses those names and their measures and limits unchanged, so that gate swaps its probe for Ouro Feel's with no rework. A component's own cases are named for what happens to it, such as `history-prepend` for MessageList.
8. **Budgets per component, checked in web's CI.** A component declares its limits in its `component.json` (`feel`), such as MessageList's `anchor-jump-px` during `history-prepend`. An app may tighten a limit, never loosen it. X-ray, the AX kit's conformance report, shows each component's budgets and its last measured values.
9. **Cheap and fast.** The Linux pass runs on pull requests that change a component with a budget. The WKWebView leg runs nightly, on release and by hand; the WebView2 leg joins it later. They use GitHub's standard runners only (`docs/ci-resources.md`), never larger ones.

## The report

Each run writes `feel-report.json`, one entry per case and engine:

```json
{ "case": "history-prepend", "component": "message-list", "engine": "wkwebview", "seed": 1,
  "measures": { "anchor-jump-px": { "value": 0, "unit": "px", "limit": 1, "pass": true } },
  "pass": true }
```

A time measure adds `runs` (every value), `median` and `spread` (the range). Beside it the runner writes `feel-report.md`, the same as a table for a job summary, and a picture of the page at the end of each case.

## Order of work

1. The probe, a MessageList `history-prepend` case and `anchor-jump-px` and `forced-layouts`, in real WKWebView on a macOS runner, run by hand.
2. The seeded data generators.
3. The scripted input: scroll with momentum, typing, switching.
4. The Linux pass on pull requests.
5. Time measures as medians of 3 or more, with spread.
6. Budgets in `component.json` for MessageList, Composer and the picture components, with an X-ray claim.
7. The WebView2 leg on a Windows runner.

## Not decided here

- Whether the probe ships as a registry item (`ouro-feel`) for apps to install, or as a release asset an app's probe service downloads by hash, as core's claim sets are.
- How the macOS host posts trackpad momentum: synthesized `NSEvent` scroll phases may not match a real trackpad's, which the first scroll case will show.

## Prior art

Read on 2026-11-04.

| Find | Verdict | Why |
|---|---|---|
| The chat app's own scroll replay and layout-cost probe | **Adopt** the case names, measures and limits | They caught the regression; Ouro Feel generalizes them so the app's gate adopts it unchanged. |
| Web's latency specs ([`site/e2e/latency.ts`](https://github.com/ourostack/ouro-ui/blob/main/site/e2e/latency.ts)) | **Borrow** | Medians over many presses after warm-ups, every sample printed. Ouro Feel keeps that for time and adds deterministic measures beside it. |
| [Android Macrobenchmark](https://github.com/androidx/androidx/blob/androidx-main/benchmark/benchmark-macro/src/main/java/androidx/benchmark/macro/StartupMode.kt) | **Borrow** | Cold and warm startup modes, a set number of iterations, frame timing from the real app: the shape of `launch-cold` and our time measures. |
| [Reassure](https://github.com/callstack/reassure) | **Borrow** | Counts renders per scenario as a stable signal beside noisy time: our `commits-per-input`. |
| [Tachometer](https://github.com/google/tachometer) | **Borrow** the stance, **ignore** the tool | Report a spread, not one number. It drives desktop browsers only, not an app's own web view. |
| [Paul Irish's list of what forces layout](https://gist.github.com/paulirish/5d52fb081b3570c81e3a) | **Adopt** | The layout-reading properties and methods the probe counts. |
| [Layout Instability API](https://github.com/mdn/browser-compat-data/blob/main/api/LayoutShift.json) | **Ignore** | Chromium only; Safari has none, so the probe measures shifts itself. |
| [Event Timing API](https://github.com/mdn/browser-compat-data/blob/main/api/PerformanceEventTiming.json) | **Watch** | Input to next paint where the engine has it: Chrome 76 and, per the same data, Safari 26.2. |
| [Speedometer](https://github.com/WebKit/Speedometer) | **Watch** | Cross-engine workloads with real frameworks; it scores a browser, not an app's feel. |
| [Lighthouse user flows](https://github.com/GoogleChrome/lighthouse/blob/main/docs/user-flows.md) | **Ignore** | Chromium only. |
| [Flashlight](https://github.com/bamlab/flashlight) | **Watch** | Scores a mobile app's performance from the device; Android only today. |
| [hyperfine](https://github.com/sharkdp/hyperfine) | **Borrow** | Warm-up runs, then the median and the range: how `launch-cold` and `launch-warm` report. |
