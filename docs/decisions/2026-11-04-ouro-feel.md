# Decision: Ouro Feel, measuring how an app feels in real use

Status: proposed, 2026-11-04. The code lives in web, `ourostack/ouro-ui`, under `feel/`; this record is its design.

## Why

Ari, 2026-11-04: "being able to measure actual usage properly so that we could have gotten this right from the very start is something we should have cheap reusable fast deterministic tooling for, as part of ouro ui, yes?"

A chat app built on Ouro UI shipped a scroll regression that unit tests and headless browsers missed. Bisecting it taught two things. Single timing runs of the same build swung from 1.3 s to 26.6 s, so one run decides nothing. The signals that did catch it were deterministic: one frame of about 9 s, and the reader's message jumping 8.5k to 11k px when older history was put in above it. Ouro Feel makes those signals cheap to get for every Ouro component and every Ouro app.

## Decision

1. **The real engine decides.** A measure that gates a release comes from WKWebView on macOS or WebView2 on Windows, the engines Ouro apps ship in. Playwright's WebKit and Chromium on Linux are a fast first pass on pull requests; they catch most regressions and decide nothing about timing.
2. **The contract is apart from the drivers.** One stack-neutral spec, [`standard/feel/feel.spec.json`](../../standard/feel/feel.spec.json) with its page [`feel.md`](../../standard/feel/feel.md), holds the scenarios, launch stages, measure definitions, seed and report. Web engines are the first driver. Native drivers plug into the same spec: AppKit and SwiftUI through XCUITest, with `os_signpost` for launch stages and `CADisplayLink` for frame timing; WinUI later. Every driver uses the same names, budgets and report, so web and native numbers compare side by side. Native drivers are on hold until web works for everyone (Ari, 2026-11-04).
3. **One probe, any host.** The meter is one plain script, `ouro-feel-probe.js`, that goes first in the page's `<head>`, before the page's own scripts. A probe service serves the page with it and drives the page by HTTP long-poll, so the runner needs nothing from whatever opened the page: Playwright for the Linux pass, a bare WKWebView host for components, or an app's own shipped web view for app gates. Input comes from outside the page (OS events, or the DevTools Input domain), and the probe reads the trusted events itself.
4. **Deterministic measures first.** Counts and pixels, which give the same answer on every run of the same build. The first app gate's names and definitions are canonical, so its gate reads the same numbers:
   - `jumps`: frames where the reader's row (the one in the middle of the list's view, followed from frame to frame) moved 100 px or more outside what the input explains (with no input, against it, or beyond its own distance); `shifts` counts 8 px or more, and `anchorShiftPx` adds the jumps up.
   - `blankFrames`: frames where none of 5 points down the list lands on a row, while the list holds rows.
   - `jumpsStrict` and `blankFramesInset`: that gate's stricter options, under their own names (a move over 2 px with no input in the last 300 ms, against the wheel, or beyond its movement; no row inside the view inset 40 px, or a placeholder in view).
   - `anchorMovePx`: how far the reader's row got from where it started, net of the input. Safari has no Layout Instability API ([MDN's compatibility data](https://github.com/mdn/browser-compat-data/blob/main/api/LayoutShift.json) lists no Safari version), so the probe measures rows itself, in every engine alike.
   - `forcedLayouts`: layout reads (the properties and methods that make the engine lay out, such as `offsetHeight` and `getBoundingClientRect()`) made while a DOM change since the last painted frame is still waiting. The probe sees a waiting change with a document-wide `MutationObserver`'s synchronous `takeRecords()`, and clears it once a frame has painted. `layoutReads` and `layoutReadsPerFrame` count all reads.
   - `deadInput`, `rowsMounted`, and later `commitsPerInput`: React commits per scripted input, from React's DevTools hook, which an injected script can install before React loads.
   - A count gates only once repeat runs show it steady: a count that depends on how work falls across frames (`forcedLayouts`, `layoutReadsPerFrame`) is reported until it is.
5. **Time measures are a median of at least 3 runs, with their spread.** Input to next paint, long tasks and launch time are reported as the median and the range of the runs, never one run. The longest frame is kept as a deterministic-enough guard: a frame over 1 s fails whatever the median says, because that is what the 9 s frame was.
6. **Seeded, made-up data.** Generators build heavy stores (long histories, many pictures and cards, live arrivals) from a seed, so every run gets the same data. Nothing comes from a real account; agents in the data have role names such as `inbox-agent`.
7. **Scripted human input from the host.** Trackpad scrolling with momentum, typing at 120 words a minute, conversation switches, cold and warm launch, a network drop and a wake. On macOS the host posts real events to its own window; the Linux pass uses Playwright's input.
8. **Cases keep the app's names.** The first app gate's cases are `launch-cold`, `switch`, `scroll` and `typing` (and, when built, `launch-warm`, `network-drop` and `wake`), and Ouro Feel uses those names and their measures and limits unchanged, so that gate swaps its probe for Ouro Feel's with no rework. A component's own cases are named for what happens to it, such as `history-prepend` for MessageList.
9. **Budgets per component, checked in web's CI.** A component declares its limits in its `component.json` (`feel`), such as MessageList's `anchorMovePx` during `history-prepend`. An app may tighten a limit, never loosen it. X-ray, the AX kit's conformance report, shows each component's budgets and its last measured values.
10. **Cheap and fast.** The Linux pass runs on pull requests that change a component with a budget. The WKWebView leg runs nightly, on release and by hand; the WebView2 leg joins it later. They use GitHub's standard runners only (`docs/ci-resources.md`), never larger ones.

## The report

Each run writes `feel-report.json`, one entry per case and engine:

```json
{ "case": "history-prepend", "component": "message-list", "engine": "wkwebview",
  "engineVersion": "…", "os": "…", "settled": true,
  "measures": { "jumps": { "unit": "count", "runs": [0, 0, 0], "median": 0, "spread": [0, 0], "limit": 0, "pass": true } },
  "pass": true }
```

Every measure carries each run's value, so an app's gate can take its own medians and bands; it holds counts and timings only, never page content. Beside it the runner writes `feel-report.md`, the same as a table for a job summary, and a picture of the page at the end of each case.

## Order of work

1. The probe, the probe service, a MessageList `history-prepend` case with `anchorMovePx`, `jumps`, `blankFrames` and `forcedLayouts`, in real WKWebView on a macOS runner, nightly and by hand.
2. The seeded data generators.
3. The scripted input: scroll with momentum, typing, switching.
4. The Linux pass on pull requests.
5. Time measures as medians of 3 or more, with spread.
6. Budgets in `component.json` for MessageList, Composer and the picture components, with an X-ray claim.
7. The WebView2 leg on a Windows runner.

## Not decided here

- Whether the probe ships as a registry item (`ouro-feel`) for apps to install, or as a release asset an app's probe service downloads by hash, as core's claim sets are.
- How the macOS host posts trackpad momentum: synthesized `NSEvent` scroll phases may not match a real trackpad's, which the first scroll case will show.

## Prior art

Read on 2026-11-04.

| Find | Verdict | Why |
|---|---|---|
| The chat app's own scroll replay and layout-cost probe | **Adopt** the case names, measures and limits | They caught the regression; Ouro Feel generalizes them so the app's gate adopts it unchanged. |
| Web's latency specs ([`site/e2e/latency.ts`](https://github.com/ourostack/ouro-ui/blob/main/site/e2e/latency.ts)) | **Borrow** | Medians over many presses after warm-ups, every sample printed. Ouro Feel keeps that for time and adds deterministic measures beside it. |
| [Android Macrobenchmark](https://github.com/androidx/androidx/blob/androidx-main/benchmark/benchmark-macro/src/main/java/androidx/benchmark/macro/StartupMode.kt) | **Borrow** | Cold and warm startup modes, a set number of iterations, frame timing from the real app: the shape of `launch-cold` and our time measures. |
| [Reassure](https://github.com/callstack/reassure) | **Borrow** | Counts renders per scenario as a stable signal beside noisy time: our `commits-per-input`. |
| [Tachometer](https://github.com/google/tachometer) | **Borrow** the stance, **ignore** the tool | Report a spread, not one number. It drives desktop browsers only, not an app's own web view. |
| [Paul Irish's list of what forces layout](https://gist.github.com/paulirish/5d52fb081b3570c81e3a) | **Adopt** | The layout-reading properties and methods the probe counts. |
| [Layout Instability API](https://github.com/mdn/browser-compat-data/blob/main/api/LayoutShift.json) | **Ignore** | Chromium only; Safari has none, so the probe measures shifts itself. |
| [Event Timing API](https://github.com/mdn/browser-compat-data/blob/main/api/PerformanceEventTiming.json) | **Watch** | Input to next paint where the engine has it: Chrome 76 and, per the same data, Safari 26.2. |
| [Speedometer](https://github.com/WebKit/Speedometer) | **Watch** | Cross-engine workloads with real frameworks; it scores a browser, not an app's feel. |
| [Lighthouse user flows](https://github.com/GoogleChrome/lighthouse/blob/main/docs/user-flows.md) | **Ignore** | Chromium only. |
| [Flashlight](https://github.com/bamlab/flashlight) | **Watch** | Scores a mobile app's performance from the device; Android only today. |
| [hyperfine](https://github.com/sharkdp/hyperfine) | **Borrow** | Warm-up runs, then the median and the range: how `launch-cold` and `launch-warm` report. |
