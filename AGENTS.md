# Ouro UI core

Core is the platform-neutral part of Ouro UI: what is true on every platform, for Ouro HX (people) and Ouro AX (agents). Today it holds the tokens and their generators, and the decision records. The HX design language, AX's claims standard and the ui.ouroboros.bot site arrive later. Platform code lives in its platform's repository: web in `ourostack/ouro-ui`, Apple in `ourostack/ouro-ui-apple`.

## Tokens

- `tokens/` is the source. `dist/` is generated by `pnpm tokens`; never edit it, and it is not committed.
- `templates/web/` holds web's stylesheets with a placeholder per value. Change a template only for prose or non-token CSS.
- `pnpm tokens:parity` must pass: `dist/web/` equals web's files at `parity.json`'s `webTag`, byte for byte. A token change lands in web first, then here with a `webTag` bump, until web builds from core.
- Before you push, run `pnpm typecheck`, `pnpm tokens`, `pnpm tokens:parity`, `pnpm test`, and on a Mac, `pnpm apple:check`.

## Ouro HX's component claims

- `standard/hx/components.claims.json` is the claim set for the components every platform shares (web's names: `button`, `empty`, `alert`, `sheet`, `toast`, `badge`, `card`, `item`); `components.md` beside it is its page, whose claims section `pnpm hx:page` renders from the JSON (a test fails when they differ). Edit the JSON, run `pnpm hx:page`, and bump the set's `version` once a release has shipped it.
- Same admission rule as AX: `must` needs a stated hazard with a check, or an evaluation. `checkHxClaimSet` in `src/hx-claims.mts` enforces the shape. Each claim's `checks` names the test that proves it on each platform; a platform adds its entry when its tests prove it.

## Ouro Feel's spec

- `standard/feel/feel.spec.json` is what every Feel driver shares: the scenario ids, launch stages, measure names and how they are judged, the seed and the report. `feel.md` beside it is its page, whose spec section `pnpm feel:page` renders from the JSON (a test fails when they differ). The design is `docs/decisions/2026-11-04-ouro-feel.md`.
- Names are stable: drivers on every stack (web's `feel/` in `ourostack/ouro-ui`, Apple's and Windows' later) and app gates report under them. Add a name here first, in its own pull request, and never rename one a driver or gate uses. Bump `version` once a release has shipped it.
- A native stack measures its components with these scenarios once its driver exists, and its components ship Feel budgets under these names.

## Ouro AX for Apple

- `standard/ax/surfaces/apple.claims.json` is the claim set; `apple.md` beside it is its page, and a test fails when their claim lists differ. Change both in one PR and bump the set's `version`.
- A claim starts as `should`. It becomes `must` only with a SiriEvaluations run that shows the failure, or a stated hazard with a check (web's admission rule). `checkAppleClaimSet` in `src/ax-claims.mts` enforces the shape, and `test/fixtures/canonical-json-vector.json` is the hash test vector every platform's copy asserts.
- Platforms vendor `dist/ax/apple.claims.json` from a release, by hash; never edit their copies.

## The one action model

- `src/actions.mts` declares an action once (`defineAction`) and generates its seven projections: CLI (`commands.json`), MCP (`mcp.json`), WebMCP (`webmcp.json`), web (`web.ts`), App Intent and SwiftUI button (`OuroActions.swift`), and Reins (`OuroActionsReins.swift`). It imports only `node:` modules, because apps vendor the file itself from a release as `ouro-actions.mts`; keep it that way.
- The fixture `test/fixtures/actions/shopping.actions.mts` and its committed `generated/` folder are the proof: `pnpm actions:check` fails CI when a generated file drifts, and the apple job builds and runs the generated Swift (`apple/actions-check`). After changing the generator, run `pnpm actions:generate` and commit the folder.
- The person-only refusal is web's refused outcome byte for byte (web's `cli.ts`); change it only together with web. `mcp.json` is the one MCP door.
- `standard/ax/actions.claims.json` is the claim set and `actions.md` its page (`pnpm actions:page`); the adopter guide is `docs/guides/actions.md`.

## Agent-composed UI (A2UI)

- `src/a2ui.mts` is Ouro HX's A2UI v1.0 catalog definition, validator, resolver and MCP Apps helpers. It imports nothing, because web vendors it byte for byte and Apple ports it; keep it that way. `src/a2ui-catalog.mts` generates catalogs (HX's, and an app's from its action set) and is released as `ouro-a2ui-catalog.mts`.
- `standard/hx/a2ui/` holds the catalogs and the conformance cases every renderer must pass. After changing either module, run `pnpm a2ui:generate` and review the diff; `pnpm a2ui:check` fails CI on drift. A case named `invalid-*` must fail validation.
- `test/fixtures/a2ui/spec/` is A2UI's own v1.0 JSON Schemas at a pinned commit (`SOURCE.md`); the tests validate both catalogs and every case against them.
- A component joins the catalog only when web's `a2ui-surface` and Apple's `OuroA2UI` both render it. The adopter guide is `docs/guides/a2ui.md`; the decision is `docs/decisions/2026-11-13-a2ui-catalog.md`.

## Claims

A factual sentence is a claim on every surface: Markdown, code comments, a pull request's title and body. Give each claim its primary source (a file, a test, a command's output or a link) and, where one exists, the check that proves it, so the next agent can trust it without rebuilding the proof. Don't reword a claim to get past review: source it, correct it, or remove it. This is web's Claims rule; its `pnpm claims:lint` tooling moves here with the standard.

## Look around first

Meerkat mode: look around first. Before you design or build something new (a component, a kit, a standard, a tool or a platform target), look for prior art to adopt or borrow, and do it again for every decision record: give the record a "Prior art" section that links each find and marks it adopt, borrow, watch or ignore (Ari, 2026-11-03: "make it a standing rule for all the ouro ui stuff!!").

## Working here

- Every change after the initial import goes through a pull request, merged when CI is green.
- Never add AI attribution to commits, pull requests, code or docs: no `Co-authored-by:` (or other `*-by:` trailer) naming an AI tool or a bot, and no "Generated with" line. CI's `attribution` job runs `scripts/attribution.mjs` over every commit a pull request adds and fails on one; commits already on main are not checked.
- Releases are tags `vX.Y.Z` matching `package.json`'s version; the release workflow attaches `dist/` to the GitHub release.
- Other agents work in web and the platform repositories. Copy first, remove later, and never rebase or force-push someone else's branch.
- Ouro uses Ari's personal Apple developer account only, never the work (Microsoft) account or anything in ~/.config/tandem-signing.
- A move, split or rename isn't done until every repository whose readers are affected says what moved, where it went and the rule for new work, in its README and AGENTS.md, in the same change. Then open an issue labelled `moved` in each old repository (create the label if it's missing), saying what moved, where it went and the rule for new work, and close it once the old home's README and AGENTS.md say so.
